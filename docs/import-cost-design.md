# 导入旧会话·省 API 三层漏斗设计（v0.4 提案）

## 问题
用户网页端 DS 历史导出 JSON 高达 28.9MB（含小说级超长上下文），全量蒸馏预计消耗巨额 API 余额，且可能中途耗尽。

## 核心原则
**「对话全文」几乎从不需要进 LLM**——记忆蒸馏需要的是「这个会话发生了什么、决定了什么、沉淀了什么」。三层漏斗把 LLM 只花在刀刃上。

## L1 标题预筛（零 API 成本）
- 会话列表接口只拿 title/updated_at/消息数（已有 fetch_page）
- 面板列出全部会话标题 + 复选框，用户勾选要导入的（默认全不选；支持按时间范围/关键词批量勾选）
- 小说类、临时问答类会话用户自己排除——用户最清楚什么值得记
- 产出：会话白名单

## L2 本地摘要卡（零 API 成本）
对白名单内每个会话，**本地代码**（不调 LLM）提取「摘要卡」：
- 首条用户消息（任务/意图）前 200 字
- 最后一条用户消息（收尾状态）前 200 字
- 助手第一条回复的首句（方案方向）前 100 字
- 会话轮数、时间跨度
- 每张卡硬上限 500 字符
- 产出：每会话 ≤500 字符的结构化摘要卡

## L3 预算封顶蒸馏（成本可控）
- **只蒸馏摘要卡**，不蒸馏全文。50 个会话 = 50×500 字 = 约 2.5 万字符 ≈ 1.5 万 token 输入，一次调用即可，成本约几分钱
- 蒸馏提示词升级：「这些是会话摘要卡，提炼跨会话的持久偏好/项目脉络/重要决定；单会话细节一律丢弃」
- **预估确认**：bridge 新增 POST /memory/import/estimate——返回本次蒸馏预计字符量/token 量，UI 显示「预计消耗 ≈X 元」让用户点确认才执行
- **双闸**：maxImportSessions（会话数）+ maxImportChars（总字符量，默认 5 万）
- **断点续跑**：按会话分批，bridge 记录已处理会话 id，中断后跳过已完成的

## 对比
| 方案 | 输入量 | 成本 |
|---|---|---|
| 全量蒸馏 28.9MB | ~2900 万字符 | 数百元 + 数小时 + 大概率中途失败 |
| 三层漏斗 | ~3-5 万字符 | **几分钱** + 分钟级 |

## 为什么不会丢有用信息
- 「值得跨会话记住的」信息高度集中在会话的「开头意图」与「结尾结论」——这正是摘要卡抓取的两端
- 超长会话（如小说创作）的正文本身不该进记忆库——记忆库要的是「用户在写小说、偏好什么题材」这类元信息，摘要卡足够
- 真正重要的会话用户可在 L1 主动勾选「深度模式」（该会话取首尾各 1000 字），实现精细化预算分配

## 实施分工
- bridge-dev：bridge 加 /memory/import/estimate 预估器 + 断点续跑 + maxImportChars 闸
- ext-dev：面板会话勾选列表（L1 UI）+ 本地摘要卡生成器（L2）+ 预估确认弹层（L3 UI）
- ext-dev 同时完成 0.3.11 三处 UI 改动的 rebase（位置上移/改名记忆设置/滚动条圆角）
